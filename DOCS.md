<a id="overview"></a>

### 1. Как работает программа

| Часть | Где находится | Что делает |
|---|---|---|
| **Прошивка ESP32** | `src/`, `include/warp/` | Подключается к Wi-Fi, проверяет сайты и управляет выбранным WARP-интерфейсом Keenetic |
| **SERVICE на компьютере** | `service.ps1`, `scripts/` | Сохраняет настройки, создаёт ключи, собирает прошивку и выполняет защищённую запись по USB |

#### 1.1. Порядок работы прошивки

1. Проверяет NVS — область flash с настройками и служебными записями.
2. Загружает параметры Wi-Fi, Keenetic, мониторинга и расписания.
3. Подключается к Wi-Fi и синхронизирует время через SNTP.
4. Проверяет **ControlUrls** — сайты для проверки обычного интернета.
5. Если доступен хотя бы один контрольный сайт, проверяет **TargetUrls** — сайты для проверки WARP.
6. Оценивает долю отказавших целевых сайтов и число неудачных циклов подряд.
7. При подтверждённом сбое выполняет восстановление: свежая проверка → чтение интерфейса → отключение → пауза → включение → ожидание → повторная проверка.
8. Передаёт общий снимок состояния в Serial и на доступный OLED.

**Перезапуск WARP** здесь означает выключение и обратное включение выбранного WireGuard-интерфейса. Полная перезагрузка роутера не выполняется.

> [!IMPORTANT]
> `parseIdentity()` разрешает конкретный профиль: **KN-4010, версия 5.1.8**. Другой профиль получает `UnsupportedRouter`. Требование KeeneticOS 5.1.x из README шире фактической проверки в коде.

#### 1.2. Как определяется сбой

| `TargetFailurePolicy` | Когда цикл считается неудачным |
|---|---|
| `0`, `Any` | Отказал хотя бы один целевой сайт |
| `1`, `Half` | Отказала как минимум половина |
| `2`, `Majority` | Отказало больше половины; значение по умолчанию |
| `3`, `All` | Отказали все |

`FailureThreshold` задаёт число полных неудачных циклов подряд; по умолчанию — **5**. HTTP-коды **200–399** считаются доступностью. Содержимое страницы не анализируется, перенаправления автоматически не выполняются.

> [!NOTE]
> Контрольные сайты должны быть доступны без WARP с учётом маршрутизации роутера. Код не создаёт для них отдельные маршруты. Если все контрольные сайты недоступны, целевые запросы пропускаются и восстановление WARP не начинается.

#### 1.3. Незавершённое отключение

До отключения `Monitor` сохраняет в NVS запись `recovery`: обязанность вернуть интерфейс во включённое состояние. Она привязана к IP, HTTPS-имени, порту и интерфейсу, читается после перезапуска ESP32 и удаляется после подтверждения включённого административного состояния.

Новое восстановление требует подтверждённого интернета. Завершение уже начатого допускается без общего интернета при доступных Wi-Fi и доверенном времени для HTTPS. `EnableAutoRecovery = 0` эту обязанность не отменяет.

#### 2.1. [service.ps1](service.ps1)

Точка входа SERVICE. Собственных именованных функций нет: файл импортирует модули и направляет `-Action` в обработчик.

| Действие | Назначение |
|---|---|
| `Menu`, `Help` | Интерактивное меню или справка; меню при необходимости запрашивает повышение прав |
| `Configure` | Ввод и проверка настроек, создание заголовков и зашифрованного NVS |
| `Inspect`, `InspectProtection` | Чтение сведений о плате или исходного состояния защиты |

| `NewDeviceKeys` | Создание связанного с устройством хранилища ключей |
| `BackupKeys`, `RestoreKeys` | Переносимая копия ключей или восстановление в новое хранилище |
| `PrepareProvision`, `Provision` | Подготовка первичного пакета или первичная защищённая запись |
| `VerifyProvision` | Проверка существующей записи и запуска без повторной записи flash/eFuse |
| `PrepareUpdate`, `Update` | Подготовка или применение подписанного USB-обновления |

Верхний обработчик печатает разрешённые сообщения, скрывая полное исключение с возможными данными ввода. Код завершения при отмене — `2`, при ошибке — `1`.

### 3. Папка src — прошивка

Здесь находится реализация, а в `include/warp/` — типы и объявления. `begin()` обычно подготавливает модуль, `tick()` продвигает работу на один шаг.

#### 3.1. [main.cpp](src/main.cpp)

Создаёт модули и связывает их между собой.

| Функция | Что делает |
|---|---|
| `app_main()` | Проверяет NVS через `initializeStorage()`, затем запускает Arduino, `setup()` и `loop()` |
| `setup()` | Загружает настройки, запускает дисплей, сеть, Keenetic, монитор, расписание и USB-обслуживание |
| `loop()` | Продвигает модули, обрабатывает расписание, выводит диагностику и отдаёт время FreeRTOS |
| `report()` | Передаёт общий снимок состояния в Serial и OLED |
| `measureConfiguration()` | Вычисляет HMAC загруженной конфигурации на ключе NVS |
| `acquireService()` | Разрешает паузу управления для обслуживания, если нет операций и обязанности восстановления; считывает дату расписания |
| `releaseService()` | Снимает паузу обслуживания |
| `serviceScheduleDate()` | Возвращает сохранённую для обслуживания или текущую дату планировщика |

После передачи учётных данных модулям временные поля конфигурации очищаются. Ожидания USB при запуске нет. Во время служебного USB-ответа обычный вывод Serial приостанавливается.

#### 3.2. [board_profile.cpp](src/board_profile.cpp)

`board::current()` возвращает профиль: 4 МБ flash, кварц 40 МГц, OLED SSD1306 **72×40**, SDA **GPIO5**, SCL **GPIO6**, адрес **0x3C**. Требуется `WARP_BOARD_C3_SUPERMINI`.

Наличие экрана на конкретной плате дополнительно проверяется по I²C.

#### 3.3. [build_contract.cpp](src/build_contract.cpp)

Функций нет. Проверки компиляции останавливают сборку при неверных версиях, стандарте C++, разметке или настройках безопасности. Контролируются проверка сертификатов и времени, сохранность NVS при старте, различия test/production.

#### 3.4. [network.cpp](src/network.cpp)

Управляет Wi-Fi, доверием к времени и последовательностью проверок сайтов.

| Функция | Что делает |
|---|---|
| `Network::begin()` | Проверяет параметры, сохраняет их и начинает подключение |
| `tick()` | Обрабатывает Wi-Fi, повторные подключения, SNTP, актуальность времени и текущий цикл |
| `invalidate()` | Отменяет проверку, отзывает подтверждение интернета и меняет поколение безопасности |
| `requestChecks()` | Запрашивает новый цикл, если нет выполняющегося |
| `startCycle()` | Сбрасывает результаты и начинает контрольный список |
| `record()` | Записывает результат запроса и обновляет счётчики |

Для доверия ко времени нужны уведомление SNTP, допустимая дата и согласованность с монотонным отсчётом. Синхронизация устаревает через **6 часов**, скачок более **2 секунд** отзывает доверие к операциям. Интервалы учитывают переполнение `millis()`.

#### 3.5. [network_protocol.cpp](src/network_protocol.cpp)

| Функция | Что делает |
|---|---|
| `net::parseUrl()` | Разбирает HTTP/HTTPS URL; отклоняет недопустимые символы, данные входа и фрагменты |
| `net::validSettings()` | Проверяет списки, таймауты, TZ и URL, запрещает повторения внутри и между списками |
| `net::ResponseHeaders::feed()` | Побайтно читает HTTP-заголовки и статус, проверяет формат и размер |

Каждый список содержит **1–8 URL**, URL — до **512 байт**. Заголовки ограничены **4096 байтами**. Тело страницы не скачивается.

#### 3.6. [network_esp.cpp](src/network_esp.cpp)

Содержит два адаптера: проверки сайтов и HTTPS-транспорт Keenetic. Ограниченные сетевые операции выполняются в отдельных задачах FreeRTOS.

| `pauseIo()` | Делает короткую паузу задачи при ожидании ввода-вывода |
| `pendingIo()` | Распознаёт просьбу Mbed TLS продолжить чтение/запись позже |

| `readWarpState()` | Начинает чтение состояния |
| `setWarpEnabled()` | Начинает изменение; приватный метод доступен `Monitor` |
| `send()` | Создаёт запрос к `/auth`, `/rci/show/version`, `/rci/show/interface` или `/rci/interface` |
| `tick()` | Продвигает challenge → login → identity → read → change → verify |
| `finish()` | Завершает операцию, очищает временные данные и при определённых ошибках блокирует команды |

`Pending` означает начало операции, а не успех. После изменения состояние читается повторно. При истечении сессии допускается одна повторная авторизация; неопределённый результат отключения не вызывает автоматическое повторение команды.

Cookie хранится в RAM. Ошибки TLS, входа, прав, профиля и формата могут блокировать клиент до исправления конфигурации и перезапуска.

#### 3.12. [scheduler.cpp](src/scheduler.cpp)

| Функция | Что делает |
|---|---|

Расписание независимо от восстановления по сбоям. **0 — воскресенье, 4 — четверг**; по умолчанию — четверг, `05:00`. Дата сохраняется до запроса, даже при пропуске из-за интернета или занятости. Повторного события в ту же дату нет; пропущенную минуту код позже не догоняет.

#### 3.13. [schedule_store.cpp](src/schedule_store.cpp)

`NvsScheduleStore::load()` читает `warp/weekly_date`, проверяет размер, сигнатуру `WSD`, версию `1` и дату. `consume()` сохраняет новую дату в little-endian с commit; повторные и более ранние даты не пишет.

Ошибка сохранения останавливает расписание до перезапуска, избегая повторных событий и постоянной записи. Мониторинг обслуживается отдельно.

#### 3.14. [display.cpp](src/display.cpp)

Нужны сборка `OLED_ENABLED=1` и включение в конфигурации. Ошибка экрана не останавливает сеть; бесконечного автоматического перезапуска I²C нет.

#### 3.16. [config_tag.cpp](src/config_tag.cpp)

`configurationTag()` вычисляет HMAC-SHA256 конфигурации. Локальные операции `bytes`, `number`, `text` добавляют байты, число little-endian и строку с длиной. Порядок полей и домен `WARP-CFG-2` совпадают с Python. Отпечаток подтверждает настройки без передачи паролей.

#### 3.17. [update_probe.cpp](src/update_probe.cpp)

Служебный USB-протокол работающей защищённой прошивки.

| Функция | Что делает |

| `sending()` | Проверяет наличие неотправленного служебного ответа |

Загружает настройки из NVS; не использует секретные заголовки обычной сборки.

### 6. Папка scripts — Python

#### 6.1. [build_guard.py](scripts/build_guard.py)

`validate_targets()` разрешает для production только известные цели сборки/анализа и отклоняет загрузку и другие цели. `configure()` читает явный признак защищённого профиля из PlatformIO и применяет эту проверку. Подключается как pre-script; устройство и секреты не читает.

#### 6.2. [inspect_board.py](scripts/inspect_board.py)

`run_read()` запускает разрешённую команду чтения esptool/espefuse и получает результат. `main()` проверяет аргументы и версии, собирает сведения о плате и выбранных eFuse в локальный каталог диагностики.

Содержимое ключевых блоков не запрашивается. Соединение с ROM сбрасывает плату.

#### 6.3. [inspect_router.py](scripts/inspect_router.py)

#### 6.4. [service_router.py](scripts/service_router.py)

| Функция | Что делает |

`DiscoveryError` обозначает ошибки обнаружения, которые можно сообщить пользователю. Выбор интерфейса сохраняется в CFG компьютера; сам список читается без изменения настроек Keenetic.

#### 6.6. [security_device.py](scripts/security_device.py)

`inspect()` считывает идентичность, геометрию flash, выбранные флаги и пустоту нужных ключевых блоков, затем применяет preflight. `main()` сохраняет новый файл evidence и не перезаписывает существующий.

Операция только читает устройство и оставляет его в ROM download mode. Наличие файла evidence не заменяет повторную проверку непосредственно перед первичной записью.

| Функция | Что делает |

| `fail()` | Выбрасывает управляемую ошибку `UpdateError` |
| `load_owner()` | Открывает хранилище и требует поддерживаемую идентичность |

`ProbeUnavailableError` означает отсутствие ответа приложения, а не неверный HMAC. Ошибку аутентификации нельзя считать основанием для первичной прошивки.

Обычный пакет меняет приложение по **0x20000**. Пакет с конфигурацией дополнительно обновляет NVS по **0x10000**, сохраняя использованную дату расписания. Ключи, загрузчик и таблица остаются прежними. Для старого приложения без maintenance-протокола код предусматривает сначала обновление приложения, затем применение CFG.

> [!NOTE]
> Итог `verified` подтверждает нужный образ, при включённом CFG — его отпечаток, а также готовность, синхронизацию времени, подтверждённый интернет и завершённый цикл с обоими списками. Он не требует доступности всех целевых сайтов и сам по себе не доказывает исправность WARP.

### 7. Папка tests — проверки

Python запускает проверки, готовит временные окружения и компилирует C++-сценарии. Файлы `*_native.cpp` выполняют реальные прикладные классы на компьютере с заменами ESP/Wi-Fi/NVS. Это **имитация оборудования**, не физическая проверка платы.

Часть тестов требует Windows DPAPI/ACL, MSVC Build Tools, CMake, установленные зависимости и заранее собранные артефакты `.pio/`. При отсутствии условий некоторые классы пропускаются через `skipUnless`.

<a id="maintenance"></a>

### 9. Что учитывать при изменении кода

#### 9.1. Если меняете настройки

Один параметр может проходить через несколько представлений:

```text
Ввод SERVICE → проверка PowerShell → сохранённый CFG → CSV/NVS
→ RuntimeConfiguration → конкретный модуль прошивки
```

Проверьте `Validation.psm1`, `State.psm1`, `Menu.psm1`, `Generation.psm1`, `service_nvs.py` и `runtime_config.cpp`. Изменение набора/порядка полей HMAC требует согласовать `configuration_tag()` и `configurationTag()`.

#### 9.2. Если меняете восстановление

Сначала сохраняется обязанность, затем допускается отключение. После ошибки не должно появляться повторное отключение вместо возврата во включённое состояние. Удаление журнала требует подтверждённого административного `up`.

Расписание только просит `Monitor` выполнить операцию. Прямой доступ к изменению интерфейса остаётся у монитора; две параллельные последовательности изменения не запускаются.

#### 9.3. Если меняете протокол или защиту

| Изменение | Какие места связаны |
|---|---|
| Модель/версия Keenetic, RCI-ответ | `keenetic_protocol.cpp`, клиент и тестовые ответы |
| Адреса/размеры flash | `partitions.csv`, настройки SDK, board profile, NVS-инструменты и оба сценария записи |
| Поля USB proof или флаги защиты | `update_probe.cpp`, `secure_update.py`, `secure_provision.py`, тесты |
| Подпись, шифрование, формат vault/backup | `security_store.py` и проверки восстановления/пакетов |
| OLED | Профиль платы, флаг сборки, runtime-настройка и тесты без OLED |

> [!IMPORTANT]
> Первичная запись и USB-обновление имеют разный объём изменений. Первичная операция очищает flash поддерживаемой чистой платы, записывает сегменты и включает необратимую защиту. Обновление ограничено приложением и при выборе CFG — NVS; eFuse не меняет.

#### 9.4. Как запускать проверки

Из корня проекта, если соответствующие инструменты уже установлены:

```powershell
# Справка SERVICE
.\service.ps1 -Action Help

# Одна тестовая сборка; без загрузки на устройство
python -m platformio run -e c3-test-no-oled

# Проверка четырёх заранее собранных окружений
python scripts/verify_stage2_builds.py

# Python-тесты; аппаратные зависимости заменены, часть тестов может быть пропущена
.\.local\service-tools\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"
```

Для проверки четырёх окружений сначала должны существовать все четыре сборки. Успешные тесты на компьютере подтверждают проверенные сценарии; физическая приёмка защищённого USB, BOOT/RESET, реальной Wi-Fi-сети и конкретного OLED выполняется отдельно на оборудовании.
